# テンプレートベースの生成デザインシステム 実装設計書

本設計書は、`backend/tests/test_api.py` に記述されたテスト仕様を**「絶対の正」**とし、それに従いながらシステムを稼働させるための方針と課題解決のアプローチを定義するものです。

## 1. ゴールと現状の整理

ユーザーが画像をアップロードするとその「レイアウト（要素の位置やサイズ）」と「デザインの雰囲気（タグ・テキスト）」を自動抽出し、以降のプロンプト入力時に最も雰囲気が合致するレイアウト構造をベクトル検索で引き当て、新しいデザイン情報（テキストや色）を付与して返すAPI（FastAPI）を実装します。

現在、`tests/test_api.py` に規定されたテストが通るようにモック（Stub）化された関数を、OpenAI API などの実際の処理に置き換えていく段階です。

## 2. ユーザー指摘の「懸念点・不可能に思える点」への回答と設計

本システムにおける技術的妥当性と、テスト仕様との整合性について以下の方針をとります。

### ① 「テンプレートが見つからない場合」とは？
**【設計方針】**
1. データベース（ChromaDB）に1件も登録されていない場合。
2. ベクトル検索を行なった際、ユーザーのプロンプトとの類似度スコア（コサイン類似度等）が**閾値（Threshold）を下回った場合**にも「適切なテンプレートが見つからなかった（＝404）」とする設計を取り入れます。これにより無関係なレイアウトが選ばれることを防ぎます。

### ② 「レイアウト構造（座標データ）」と「雰囲気」の抽出について
**【設計方針】**
1. **レイアウトの詳細化:** テスト仕様書には `x, y, width, height` と `font_color` のみが確認されていますが、これは「最低限必ず含めること」の制約にすぎません。実装（`llm.py`）では、OpenAI Vision API に対して「文字のフォントサイズやパディング、マージンも含めたJSONを返すように」明示的にプロンプトで指示します。
2. **雰囲気（Atmosphere）の意味:** これは「画像のスタイル、配色、トーン」を示す**自然言語の文字列**（例: `「明るい春らしさを感じる、ピンクベースのセールのポスター」`）を指します。

### ③ 「ベクトル検索で適したレイアウトが引けるのか？（タグ入力の必要性）」
**【設計方針】**
ユーザーのおっしゃる通り、座標の数字に対してはベクトル検索は機能しません。
そのため、テストコードでは `extract_template_structure` から「レイアウトJSON」と同時に**「雰囲気を示すテキスト（Atmosphere）」**を分離して取得しています。ベクトルDBにはこの「雰囲気テキストのEmbedding（ベクトル）」を保存します。
実質的に**「Vision LLMがアップロード時に画像から『自動的に複数タグ・説明文』を推定生成し、それを元にベクトル検索する」**仕組みになるため、ユーザーに手動でタグを入力させるのと同じ精度の検索結果を全自動で実現可能な設計になっています。

### ④ 今回の目的達成において「実現できること」と「実現できない（非常に困難な）こと」の明確化

ご要望通り、本システムのアーキテクチャ（APIとLLMを組み合わせたテスト仕様に基づく構成）において、技術的に達成可能な範囲と不可能な範囲を以下に明確に切り分けます。

#### ✅ 実現できること（スコープ内）
1. **相対座標によるレイアウト構造の抽出と維持:** （合意済）画像サイズに依存しない相対座標（比率・パーセンテージ）として要素の位置・幅・高さを柔軟に出力し、フォーマットを維持したままJSONを生成すること。
2. **意味的タグ（Atmosphere）の自動抽出とベクトル検索:** ユーザー指定のタグがなくても、Vision APIが「画像のシーン、トーン、目的」テキストを構築し、それを検索インデックスとして高速に類似テンプレートを引くこと。
3. **内容の動的差し替え（Generative Design）:** テキストの中身（キャッチコピー等）や、要素のテーマカラーなど、レイアウト構造を崩さずにテキスト・属性値パラメータをユーザーのプロンプトに合わせて上書き生成すること。

#### ❌ 実現できないこと・非常に困難なこと（スコープ外）
1. **画像ファイル（PNG等）の「最終レンダリング出力」までAPI単体で行うこと:** 
   対象のテストケース（`test_api.py`）が到達点としているのは**「構造化されたJSONの返却」**までです。取得したJSON（相対座標とテキスト）を配置して画像ファイルとして描画・合成し直す機能には、クライアント側（CanvasやFabric.js等）またはPillowを利用した別レイヤーの描画エンジンが必要であり、本API単独では画像を返しません。
2. **文字数に起因するレイアウト崩れの「完全」自動回避:** 
   元テンプレートが「短い単語」用だったデザインの場所に、プロンプト指示によって「非常に長い文章」が生成された場合、LLMへの指示だけでは「文字サイズを自動で縮小して綺麗に収める」といった物理演算レベルの調整は完全には担保できません。（フロントエンドレンダリング時のTextFit処理等に依存します）
3. **「見えないメタデータ」（元のフォントファイル名や詳細なパス指定）の抽出:**
   「明朝体・ゴシック体」などの特徴は推定できますが、「Helvetica Neue 55 Roman」といった特定のフォントファイル名までは画像解析だけでは逆算できません。

## 3. 必要な実装ステップ

### [MODIFY] `backend/app/llm.py`
OpenAIのAPIを利用し、現在スタブになっている箇所を実装します。
- **`extract_template_structure()`**: Visionモデルを用いて、パディングやフォント指定を含んだ相対座標の `(レイアウトのJSONオブジェクト, 画像の雰囲気を表す説明文)` をタプルで返す処理を追加。
- **`get_embedding()`**: `text-embedding-3-small` などを使用して入力テキストをベクトル変換。
- **`generate_new_design()`**: `gpt-4o` 等を用い、現在の構造データに対してユーザープロンプト（例「春のPOPにして」）を踏まえた色・テキスト情報の流し込みを行う処理を追加。

### [MODIFY] `backend/app/vector_store.py`
検索クエリに基づくChromaDBの検索ロジックに「スコアの閾値チェック」を追加し、全く合致しない場合は None を返す。
